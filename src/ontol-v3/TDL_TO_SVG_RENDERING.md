# Рендер TDL в SVG

Этот документ описывает текущий пайплайн рендера Ontol v3: как `.tdl`-файл
превращается в итоговую SVG-диаграмму.

## Область ответственности

Рендер преобразует TDL-текст в SVG UML-диаграмму классов. Он отвечает за:

- чтение семантической модели, полученной из TDL;
- валидацию диаграммы;
- запрос раскладки у Graphviz;
- отрисовку UML-блоков и отношений;
- размещение кратностей и подписей отношений;
- добавление SVG data-атрибутов для обратного парсинга;
- подключение CSS-темы внутрь SVG.

Рендер не генерирует PlantUML и не использует PlantUML-сервер.

## Входы и выходы

Вход:

- TDL-текст;
- опциональное имя SVG-темы, сейчас доступны `light` и `yellow`.

Выход:

- SVG-текст;
- опциональные предупреждения;
- опциональная диагностика планарности при использовании
  `tdl_to_svg_analyzed()`.

## Общий пайплайн

```text
Текст TDL
-> лексический анализ
-> parse_tdl
-> AST
-> build_diagram
-> validate_all
-> анализ планарности
-> diagram_to_graphviz_svg
-> SVG
```

Основные публичные функции:

- `uml_dsl.tdl_run.tdl_to_svg()`;
- `uml_dsl.tdl_run.tdl_to_svg_analyzed()`;
- `uml_dsl.graphviz_render.diagram_to_graphviz_svg()`;
- `uml_dsl.diagram.ClassDiagram.to_svg()`.

## Этап 1: лексический анализ

`tdl_lexer.lex()` преобразует исходный текст в токены.

Лексер распознает:

- ключевые слова TDL, например `КЛАСС`, `АССОЦИАЦИЯ`, `ОБОБЩЕНИЕ`;
- идентификаторы;
- строки и числа;
- операторы отношений, например `->` и `--`;
- маркеры видимости;
- скобки и пунктуацию;
- синтаксис кратностей.

Лексер не зависит от рендера. Его результат - только поток токенов.

## Этап 2: парсинг

`tdl_parser.parse_tdl()` читает токены и строит AST-документ `Document`.

Парсер понимает объявления:

- классов;
- enum;
- атрибутов;
- операций;
- ассоциаций;
- агрегаций;
- композиций;
- зависимостей;
- обобщений;
- реализаций;
- опциональных команд раскладки.

Синтаксические ошибки останавливают обработку до начала сборки модели.

## Этап 3: сборка модели

`tdl_build.build_diagram()` преобразует AST-объявления в Pydantic-объекты.

На этом этапе текстовые объявления превращаются в:

- `ClassDiagram`;
- `Class`;
- `Attribute`;
- `Operation`;
- `Association`;
- `Dependency`;
- `Generalization`;
- `Realization`;
- `MultiplicityRange`.

Также здесь TDL-значения приводятся к внутренним enum-значениям и объектам
концов отношений.

## Этап 4: семантическая валидация

`ClassDiagram.validate_all()` проверяет модель до рендера.

Слой валидации ловит ошибки, которые не являются просто синтаксическими:

- ссылки на неизвестные классификаторы;
- циклы наследования;
- конфликты множественного наследования;
- некорректное использование композиции;
- неизвестные типы атрибутов и параметров операций;
- некорректные ссылки переопределения.

Если валидация не проходит, рендер останавливается, а вызывающий код получает
ошибку модели.

## Этап 5: анализ планарности

`tdl_to_svg_analyzed()` запускает `uml_dsl.planarity.analyze()` перед рендером.

Если граф планарный и позиции можно получить:

- модуль планарности вычисляет позиции классов;
- заполняется `diagram.positions`;
- выставляется `diagram.manual_layout = True`;
- рендер использует эти позиции напрямую.

Если граф непланарный:

- диаграмма все равно рендерится;
- результат содержит диагностику: `K5`, `K3,3`, имена классов, сообщение,
  подграфы и количество найденных проблем;
- общее приложение может показать предупреждение и подсветить классы, связанные
  с препятствием планарности.

Сам рендер при этом остается тем же. Планарность влияет только на выбор позиций
и на наличие диагностических данных.

## Этап 6: раскладка Graphviz

В обычном пути рендера `graphviz_render.py` строит DOT-граф из диаграммы.

Graphviz используется для:

- позиций узлов;
- маршрутов ребер;
- геометрии SVG path;
- стабильных размеров диаграммы.

Пакет вызывает системный бинарь `dot`. Graphviz является системной зависимостью,
а не Python-пакетом.

Рендер запрашивает у Graphviz:

- `svg`-вывод, из которого извлекаются реальные пути ребер;
- `plain`-вывод, который используется для сопоставления координат Graphviz с
  позициями классов и опорными точками маршрутов.

## Этап 7: отрисовка блоков классов

Блоки классов и enum рисуются слоем модели, в основном в `models.py`.

Сгенерированный SVG содержит:

- группу для каждого классификатора;
- прямоугольник заголовка;
- секции атрибутов и операций;
- текстовые строки признаков;
- бейдж типа элемента;
- блок template-параметров при необходимости;
- прозрачный bounding box для выбора/взаимодействия;
- data-атрибуты для обратного парсинга.

Рендер добавляет CSS-классы к SVG-элементам, чтобы темы могли менять цвета и
обводки без изменения логики рендера.

## Этап 8: отрисовка отношений

Отношения рисуются в `graphviz_render.py`.

Поддерживаемые типы отношений:

- association;
- aggregation;
- composition;
- dependency;
- generalization;
- realization.

Когда Graphviz возвращает путь ребра, рендер использует его. Если путь получить
не удалось, используется запасной вариант: простой маршрут между границами блоков
классов.

UML-маркеры определяются внутри SVG `<defs>`:

- пустой и закрашенный ромб;
- закрашенная стрелка зависимости;
- пустой треугольник обобщения/реализации.

## Маршрутизация ребер

Текущий рендер извлекает пути ребер из SVG-вывода Graphviz и сопоставляет их с
отношениями диаграммы.

Это улучшает визуальную маршрутизацию: итоговый SVG использует spline/path
геометрию, рассчитанную Graphviz, а не только прямые линии между блоками.

Также рендер сохраняет опорные точки из `plain`-вывода Graphviz как запасной вариант
для размещения подписей и простой отрисовки линий.

## Кратности и подписи

Кратности размещаются рядом с концами отношений.

Для Graphviz-путей позиция подписи рассчитывается с учетом:

- положения endpoint;
- локального направления path;
- приблизительной ширины текста;
- длины path;
- небольшого смещения от ребра.

Для запасной ломаной линии подписи ставятся по первому или последнему сегменту
маршрута.

Название отношения и stereotype зависимости размещаются около середины ребра
или path.

## SVG-темы

Темы находятся в:

```text
uml_dsl/styles/
```

Текущие темы:

- `light`;
- `yellow`.

Рендер загружает выбранный CSS-файл и встраивает его прямо в SVG. Поэтому
сгенерированная диаграмма переносима: SVG содержит нужные стили внутри себя.

Корневой SVG содержит:

```xml
class="uml-diagram"
data-theme="light"
data-title="Диаграмма TDL"
```

или имя выбранной темы и заголовок конкретной диаграммы.

## Data-атрибуты

SVG-вывод содержит data-атрибуты, которые использует `svg_parser.py`.

Они позволяют восстановить:

- имена классификаторов;
- видимость и кратность классификаторов;
- стереотипы, абстрактность и тип классификатора;
- атрибуты, их видимость, область действия, тип, кратность, начальное значение,
  изменяемость и `redefines`;
- операции, параметры операций, типы возвращаемых значений, свойства `query`,
  `leaf`, `abstract`, `concurrency` и `redefines`;
- значения перечислений;
- tagged values и параметры шаблонов;
- тип отношения;
- концы отношения;
- кратности;
- роли;
- навигацию полюсов ассоциации;
- тип агрегации или композиции;
- дополнительные данные полюсов ассоциации: видимость роли, collection kind,
  changeability, qualifiers, subsets, union, redefines и role type;
- stereotype зависимости;
- информацию об обобщениях и реализациях.

Поэтому рендер является не только визуальным слоем. Он также сохраняет
семантические метаданные для roundtrip-сценариев.

`svg_parser.py` после восстановления модели запускает `validate_all()` и
возвращает ошибки через `ParseResult.errors`. Для визуального roundtrip
восстановленная диаграмма помечается как `manual_layout=True`, чтобы повторный
рендер использовал позиции из SVG.

## Обработка ошибок

Рендер может завершиться ошибкой на разных этапах:

- ошибка лексера;
- ошибка парсера;
- ошибка модели или валидации;
- отсутствует Graphviz `dot`;
- ошибка выполнения Graphviz.

Автономные функции пробрасывают ошибки напрямую. Общее приложение ловит их в
`render_v3.py` и возвращает как ошибки сборки.

## Интеграция с workbench

Внутри общего приложения путь такой:

```text
.tdl -> ontol-v3 -> SVG + опциональная планарность
.ontol -> ontol-v1 -> JSON + PlantUML + PNG
```

TDL-файлы не проходят через PlantUML. Путь v3 возвращает SVG напрямую.

## Проверка рендера

Автономный набор тестов Ontol v3 запускается из `src/ontol-v3`:

```bash
python run_tests.py
```

Для рендера и roundtrip-пути проверяются:

- генерация SVG через CLI и Python API;
- темы `light` и `yellow`;
- маркеры ассоциаций, агрегаций, зависимостей, обобщений и реализаций;
- вывод кратностей и имен отношений;
- наличие data-атрибутов, нужных для обратного SVG-парсинга;
- восстановление диаграммы из SVG, включая атрибуты, операции, параметры,
  перечисления и скрытые метаданные модели;
- работа анализа планарности вместе с рендером.

## Текущие ограничения

- Импорт TDL между файлами не реализован.
- Обратный SVG-парсинг зависит от data-атрибутов, которые генерирует этот
  рендер.
- SVG без структурных `data-*` не может быть восстановлен полностью: видимый
  текст блоков не используется как источник истины.
- При планарной раскладке используется другой источник позиций, поэтому маршруты
  ребер в режиме ручной раскладки могут быть проще.
- Выбор темы доступен в автономном Streamlit-приложении, но общий workbench
  сейчас использует тему по умолчанию.
